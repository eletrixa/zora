## Behaviour

1. **Run rows.** `RunKind` becomes `"full" | "delta" | "category"`; `RunRow` gains `category1: string | null`. `insertRunStatement(db, run)` returns the prepared `INSERT INTO sync_runs (run_id, kind, status, started_at, page_size, updated_since, category1) VALUES (?1, ?2, 'running', ?3, ?4, ?5, ?6)` so `startCategoryWalk` can put 38 of them in one `db.batch`; `insertRun` becomes `insertRunStatement(...).run()`. Every read of a run row selects `category1` too.
2. **The page.** In `fetchPage` the query gains `category1` when the run has one (`{ limit, category1?, updatedSince?, cursor? }`, same order of the optional spreads as today). After the `MISSING_CURSOR` check, a category run calls `tagProducts(deps.db, runId, run.category1, ids, now)` with the page's product ids instead of `catalogue.upsertProducts`; every other kind keeps the upsert. A category run with `category1` null is a programmer error: throw, like `no sync run` today. Everything else in `fetchPage` (page halving on `15:36OUT` and `INTERNAL_SERVER_ERROR`, the restart on a refused cursor, the counts, the cursor, `last_page_timestamp`, the idempotent step) stays as it is and applies to category runs.
3. **The tags.** `src/sync/tags.ts` is SQL only and imports nothing from `walk.ts`. `tagStatement(db, productId, category1, runId, at)`: `INSERT INTO product_categories (product_id, category1, run_id, tagged_at) SELECT ?1, ?2, ?3, ?4 WHERE EXISTS (SELECT 1 FROM products WHERE id = ?1) ON CONFLICT (product_id, category1) DO UPDATE SET run_id = excluded.run_id, tagged_at = excluded.tagged_at` (the `SELECT ... WHERE` form is what SQLite needs for an upsert over `INSERT ... SELECT`; the `EXISTS` keeps a product the catalogue does not hold out, which D1's foreign key would also refuse and bun:sqlite would not). `tagProducts(db, runId, category1, productIds, at)`: one `db.batch` per page, at most one statement per id, no batch for an empty page. `untagOthersStatement(db, category1, runId)`: `DELETE FROM product_categories WHERE category1 = ?1 AND run_id != ?2`.
4. **The finish.** In `finishRun`, a category run does one batch of `untagOthersStatement(deps.db, category1, runId)` plus the `UPDATE sync_runs SET status = 'complete', finished_at = ?1 WHERE run_id = ?2`, then returns `{ status: "complete", pages, products, watermark, retired: null }` without calling `retireUnseen` and without writing the watermark (one category cannot vouch for the whole catalogue). The watermark value is computed as today from `last_page_timestamp`; it is just not written. A failed or crashed category run never reaches the delete, so yesterday's tags of that category stay.
5. **The cycle.** `src/sync/category.ts` (no `cloudflare:workers` import): `CATEGORY1_VALUES` is the guide's 38 values with `things-to-do` first, then the other 37 in the guide's alphabetical order (air-inclusive, all-inclusive, auto-and-home-improvement, automotive, baby-kids-and-toys, beach-destinations, beauty-and-spas, casinos, city, cruises, culinary, electronics, entertainment-and-media, family-trips, food-and-drink, for-the-home, gift-cards, grocery-and-household, health-and-beauty, health-and-fitness, home-improvement, hotel-travel, jewelry-and-watches, luxury, mens-clothing-shoes-and-accessories, outdoor-activities-recreation, personal-services, pet-supplies, retail, romantic, spa-and-wellness, sports-and-outdoors, toys, unique-lodging, v1-personalized-items, waterparks, womens-clothing-shoes-and-accessories); check every one against the guide and fix the list from the guide if the guide disagrees. `interface CycleParams { readonly cycle: true; readonly runIds: readonly string[] }`. `categoryRunId(cycleId, category1)` is `` `${cycleId}-${category1}` ``. `runCategoryCycle(deps, runIds, stepsFor: (runId) => StepRunner): Promise<{ complete: number; failed: number }>` walks each run in order with `runWalk(deps, runId, stepsFor(runId))`; a walk that answers `failed` counts as failed and the cycle goes on; a throw (the step retries were spent) is logged with `console.error(JSON.stringify({ at: "sync.categoryCycle", runId, error }))`, recorded through a `record-crash` step that calls `failRun(..., { code: "CRASH", ... })` when the row is still running, and the cycle goes on. One bad category must not cost the other 37 their daily tags.
6. **The job.** `startCategoryWalk: Job` (`job: "category-walk"`), next to `startFullSync` and reusing its helpers: (a) a full load `running` and younger than `FULL_RUN_GUARD_MS` answers `ok: false`, `A full load started at <started_at> is running, so the category walk waits for tomorrow.` (two walks in two isolates would send two requests per second; the weekly full load takes precedence); (b) category runs `running` younger than `CATEGORY_CYCLE_GUARD_MS` (6 hours) answer `ok: false`, `A category walk started at <started_at> is still running, so no new one was started.`; older ones are failed with code `STALE`, message `still running after 6 hours, replaced by a new category walk`; (c) `cycleId` is `` `category-${crypto.randomUUID()}` ``, `runIds` are `CATEGORY1_VALUES.map((c) => categoryRunId(cycleId, c))`; (d) one `db.batch` of 38 `insertRunStatement`s with `kind: "category"`, `updatedSince: null`, `category1: c`, the page size from `pageSizeOf(env)`; (e) `env.SYNC_WORKFLOW.create({ id: cycleId, params: { cycle: true, runIds } })`; on a throw, every run is failed with code `WORKFLOW_CREATE` (same log line as `startFullSync`) and the summary is `The category walk <cycleId> could not start: <message>`; (f) success: `Category walk <cycleId> started: 38 categories, things-to-do first, <pageSize> products per page.`
7. **The Workflow.** `CatalogueSyncWorkflow` accepts `SyncParams | CycleParams`. A cycle payload (`"cycle" in event.payload`) runs `runCategoryCycle(deps, runIds, (runId) => ({ do: (name, fn) => step.do(`${runId}:${name}`, fn) }))` so step names stay unique across the instance, logs `{ at: "sync.workflow", cycle: event.instanceId, outcome }` when any run failed, and returns. The single-run body stays exactly as it is.
8. **The status.** `getSyncStatus` selects `WHERE kind IN ('full', 'delta')`: `SyncRunRow.kind` is `"full" | "delta"` and 38 category rows a day would push the real runs out of the 20 the scorecard shows.
9. **Pacing.** Nothing new: the partner client paces one request per second and the steps of one instance run one after another. Do not add sleeps.
